## H.265 broke video: device mislabels the stream, gl-pion can't carry it

The user reported that video stopped after switching the codec to H.265. Root causes, verified on the device (V1.10.1):

- **Direct:** `/api/media/ws` still offers `h264` (profile 42E01F) but sends H.265 (NAL types 32/33/34/19).
  - We trusted the offer, so VideoToolbox was fed HEVC data as avc1.
  - **Fix:** `annexb::sniff_codec` reads keyframe parameter sets, and `direct.rs` relabels the codec. Result: 60 fps H.265.
- **Pion:** gl-pion answers only H.264 (PT 108) and then sends **no RTP at all** while the encoder is on H.265; str0m traces show only STUN/RTCP.
  - **Fix:** `Transport::for_codec` makes H.265 over Pion fall back to Direct. The GUI shows a notice and the confirm text was updated.
  - I tried and reverted a str0m H.264 depacketizer patch that would accept NAL type 0. It is pointless because no packets arrive.
- **Janus:** H.265 works (57 fps).
- **Sniff gotcha:** an H.264 slice with nal_ref_idc 2 (0x41..0x45) looks like an H.265 parameter set by type, so the sniff also requires a second header byte of 0x01.
- **Web app:** the device's own Direct player forces `video_format=0` before it streams.
- **Testing gotcha:** `timeout` without `-k` hangs on `view --bench` when SIGTERM is ignored. One killed run left the device on H.265 for about 10 min; always use `timeout -k`.
